# Практика 23 — Контейнеризация приложений с Docker

## Описание

Практика 23 продолжает реализацию балансировки нагрузки из практики 22, но теперь с использованием **Docker Compose**. Вместо ручного запуска серверов на разных портах, каждый компонент системы — отдельный Docker-контейнер.

## Архитектура

```
┌─────────────────────────────────────────┐
│         Клиент (localhost:80)           │
└────────────────┬────────────────────────┘
                 │
         ┌───────▼────────┐
         │  Nginx (80)    │ ← Балансировщик
         │  (контейнер)   │   нагрузки
         └───┬────────┬───┘
             │        │
    ┌────────▼──┐  ┌─▼─────────┐
    │ Backend1  │  │ Backend2   │
    │ (3000)    │  │ (3000)     │
    │ Docker    │  │ Docker     │
    └───────────┘  └────────────┘
```

## Ключевые технологии

### Docker
- **Контейнеризация** — упаковка приложения со всеми зависимостями
- **Dockerfile** — инструкции для сборки образа
- **Docker Compose** — оркестрация нескольких контейнеров

### Docker Compose элементы

| Элемент | Описание |
|---------|---------|
| `services` | Определение всех контейнеров (backend1, backend2, nginx) |
| `networks` | Создание виртуальной сети для связи контейнеров |
| `environment` | Переменные окружения (SERVER_ID, PORT) |
| `ports` | Проброс портов с хоста в контейнер |
| `volumes` | Монтирование файлов (конфиги) в контейнер |
| `depends_on` | Порядок запуска сервисов |

### Сеть Docker

Все контейнеры в одной сети **app-network** видят друг друга по имени:
- `backend1:3000` → IP контейнера backend1
- `backend2:3000` → IP контейнера backend2

Nginx обращается к ним по имени, Docker сам разрешает имена в IP-адреса.

```bash

docker compose down -v
```

## Тестирование отказоустойчивости

### Остановка одного backend-сервиса

```bash
# Остановить backend1
docker compose stop backend1

# Остановить backend2
docker compose stop backend2
```

### Проверка поведения

```bash
# После остановки одного сервера
for i in 1 2 3 4 5; do
  curl -s http://localhost/ | grep server
done
```

**Поведение:**
- Nginx замечает ошибки (max_fails=2)
- После 2-3 неудачных попыток исключает сервер из пула
- Все запросы идут только на живой сервер
- При перезапуске сервера он снова добавляется в пул

### Возобновление работы

```bash
# Перезапустить все сервисы
docker compose up -d

# Или перезапустить конкретный сервис
docker compose restart backend1
```

## Как это работает

### При запуске docker compose up

1. **Docker собирает образы**
   - Для backend1 и backend2 выполняет инструкции из Dockerfile
   - Использует готовый образ `nginx:alpine` для Nginx

2. **Создаёт контейнеры**
   - backend1 контейнер (порт 3000 внутри)
   - backend2 контейнер (порт 3000 внутри)
   - nginx контейнер (порт 80 → хост:80)

3. **Создаёт сеть**
   - app-network с драйвером bridge
   - Все контейнеры подключаются к этой сети
   - Docker включает DNS для разрешения имён сервисов

4. **Запускает контейнеры в порядке зависимостей**
   - Сначала backend1 и backend2
   - Потом nginx (зависит от них через depends_on)

### Как Nginx видит backend'ы

В nginx.conf используется:
```nginx
upstream backend_cluster {
    server backend1:3000;  # имя сервиса + порт внутри контейнера
    server backend2:3000;
}
```

Docker автоматически:
1. Разрешает `backend1` в IP-адрес контейнера backend1
2. Разрешает `backend2` в IP-адрес контейнера backend2
3. Nginx направляет запросы по round-robin

## Преимущества Docker Compose

| Без Docker | С Docker Compose |
|-----------|-----------------|
| Ручной запуск каждого сервера | Одна команда: `docker compose up` |
| Зависимости на хосте | Всё внутри контейнеров |
| Конфликты портов | Изоляция портов |
| Разные окружения | Одинаковое везде |
| Версии зависимостей | Контролируемые версии |
